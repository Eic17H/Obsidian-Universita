Algorithm. We "came up with" KDE Trees because we needed them for an algorithm. What algorithm? (forse si chiamano KD non KDE)

First, algoirthm to build a kde tree:
* **Input**: a set of points $P$, the current depth $d$.
* **Output**: The root of a kd-tree tree storing $P$.
* If $P$ contains only one point:
	* **Return**: a leaf storing this point.
* Else:
	* If $d$ is even (first step is zero):
		* Split $P$ into two subsets with a vertical line $l$ using the median $x$-coordinate of the points in $P$; let $P_1$ be the set of points to the left of $l$, let $P_2$ to the right.
	* Else:
		* The same with $y$.
* Recurse on $(P_1,d+1)$ and $(P_2,d+1)$, yielding $\nu_l$ and $\nu _r$.
* Create a node $\nu$ containing $l$, make $\nu _l$ its left child and $\nu_r$ its right child.
* **Return** $\nu$.

How expensive is it to find the median? You need to sort them, $O(n\log n)$. Ma Scateni ha detto che è $O(n)$. Because we need to know it in the algorithm, we need to pre-sort the set. Once in $x$ and once in $y$. It costs $O(n \log n)$. If the points are sorted, finding the median costs $O(1)$ (if you already know how long the list is). Also with an even amount of elements we define the median as the least one of the ones in the center. After shrinking the set, we get a subset of the set, but it's still sorted.

Also the median is in the left subtree.

The total computational complexity is $O(n \log n)$, because the most expensive step is sorting the set.

Memory footprint? Are we replicating any data? How many times are we storing each point? I only store points in the leaves, everything else is just indices. Linear, $O(n)$.

Now, algorithm **SearchKdTree**:

* **Input**: $\nu$ root node of the kd-tree, $R$ a range.
* **Output**: All points at leaves below $\nu$ that lie in the range $R$.
* **If** $\nu$ is a leaf:
	* **If** $\nu$ lies in $R$: $O(1)$
		* **Report** the point stored at $\nu$.
* **Else if** $region(\nu.leftChild)$ is fully contained in $R$: $O(1)$
	* $ReportSubtree(\nu.leftChild)$.
	* **Else if** $region(\nu.leftChild)$ intersects $R$:
		* searchKdTree(v.left,R)
	* if region(n.right) is fully contained in R
		* report subtree v.right
		* else if region(v.right) intersects R
			* searchKdTree(v.right, R)

Computational comlexity=??? It's hard because it's different from what we're used to. Why is it different? One part is different. The problem is that one part of the complexity is $O(k)$, where $k$ is the size of the *output*.

> Can you believe me if I tell you the computational complexity is $O(\sqrt n)$?

In total it's $O(\sqrt n + k)$.

So, we build in $O(n \log n)$ in time and $O(n)$ in space, and we search in $O(\sqrt n + k)$ Are we satisfied? No. We're used to searching in $O(\log n)$. Is there much difference?$$\begin{matrix*}[l]
n & \sqrt n & \log n \\
100 & 10 & 9 & \text{not bad} \\
10^6 & 10^3 & 19 & \text{already quite different}\\
10^{10} & 10^5 & 33
\end{matrix*}$$
KD trees are useful for when you're scanning something big like a building and you have a massive cloud of points. Passing from $10^5$ units of time to $33$, it's a big different, almost four orders of magnitude.

With our $O(\sqrt n + k)$, the problem arises when $k \ll \sqrt n$.

So, we need to find something better than a KDE Tree, and this data structure is what we call a range tree.

# Range trees

Do you remember how we perform an interval search in 1D? BST, split node, subtrees. Let's try to match it 1-to-1 with a 2D search.

1D range search:
* **Input**: A set of $n$ points $P$, an interval $[x,x']$.
	* Build a BST on $x$'s (easy).
	* Go left and search for $x$.
		* Any time you go to the left child, report the right subtree.
	* Same with right and $x'$.
		* Same with right and left.

The part where we actually report the points that are in the interval is "report the subtree". In 2D we can't simply report the subtree, because we need to consider the $[y,y']$ range. And so we can do a simple thing: let's a second step.

2D range search:
* Build a BST on $y$'s.
* Associate to each internal node a ==secondary== BST built on $y$'s.

The secondary BST has the same nodes as the primary BST, but in different positions.

So, instead of reporting a subtree during the $x$ search, we perform a 1D $y$ search on each of those subtrees.

What is the problem with this solution? There has to be a tradeoff. We pay a lot for memory occupation. At each level of the primary tree, the secondary trees occupy $O(n)$. It's $O(n \log n)$ in space.

So, building is $O(n \log n)$ in both time and space, while searching is $O(\log ^ n + k)$. Memory used to be a real problem.

> The first job I did when I was a student, I was working for a funeral home in my hometown. They spent millions of liras to expand their storage and by a hard disk storing... $20\text{ MB}$.

Nowadays, space is a much smaller problem. You never go out of core, while back then it was common.

So, KDE Tree if you need to save on memory occupancy, range tree if you need to save on time.

It's what we call a multilevel data structure, because it has one level per coordinate. Of course it can be extended to any number of dimensions.
