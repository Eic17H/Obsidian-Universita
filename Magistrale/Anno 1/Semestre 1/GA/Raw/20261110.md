# KDE Tree

An algorithm or a data structure? A data structure, of course, but we will also see algorithms that use it. If you don't describe how to use it, a data structure is useless. Describing how to use it has two steps: how and why you build it, and how you use it. The two ways to use it is to put data in (build and update) and take data out (read). We'll see that KDE trees aren't a very dynamic data structure.

So, data structures. Operations:
* Build
* Update
* "Use" (search)

What is the motivation behind designing a new data structure? Secondo me, perché serve in un algoritmo, come abbiamo visto per la DCEL. We were trying to look for a way to interval search in 2D. We saw how to interval search in 1D using a BST, but that's not enough for 2D.

Let's take a random set of points in the plane. The same type of input as for the convex hull problem.

What can be a search in 2D? How can I describe it? For the simple search, you just input coordinates (a pair of numbers) and return whether it is in the set (a bool), or its value. If the data is unsorted, you can do nothing but look through all points. What if you want to sort them to accelerate the search? As we saw for the convex hull, if we want to sort a set of pairs, there are multiple ways (sort by $x$, by $y$, by $x+y$, by any function $f(x,y)$), but none is one-size-fits-all. If my set is sorted in $x$, the search for the first coordinate is $O(\log n)$, but the search for the second coordinate is still $O(n)$.

Sorting in $x$ and sorting in $y$ for elements with the same $x$ can work for a simple search, but not for the interval search.

This geometric way of thinking about a search isn't always used. When querying a database, you take an interval on one key, an interval on another key, and intersect the two resulting sets, that's not explained using geometry but it is the exact same as a Cartesian product in geometry. That's two range searches.

A first idea (da un collega) would be to have two BSTs (one per dimension), range search on both, and intersect. That is:

1. Build step:
	1. Build a BST $XB$ on $x$'s;
	2. Build a BST $YB$ on $y$'s.
2. Search step:
	1. 1D search on $XB$;
	2. 1D search on $YB$;
	3. Intersect the results.

Question number 1: does it work (does it find the solution (effectiveness))? Yes. Second question: is it efficient (efficiency)? Well:

1. $O(n \log n)$ time, $O(n)$ space
	1. $O(n \log n)$ time, $O(n)$ space
	2. $O(n \log n)$ time, $O(n)$ space
2. $O(\log n + k k')$
	1. $O(\log n + k)$
	2. $O(\log n + k')$
	3. $O(k k')$

In total, $O(n \log n + kk')$. Unless I'm sure that the amount of pairs is always going to be very very small, that $kk'$ makes the algorithm too slow.

No two points share the same $x$ or the same $y$. Take the median on $x$, draw a vertical line through it, and you have two half-planes. With the usual BST, each half-plane becomes a subtree, and I'd recursively apply the algorithm. For the KDE tree, I use the $y$ coordinate in the second step instead of the $x$ coordinate, basically rotating my graph 90°.

Draw a vertical line going through $H$ that splits the whole plane. Then draw horizontal lines through $C$ and $E$, each limited to its half-plane. Then, on the left, $C$ and $D$, and on the right $E$ and $F$. Then vertical again. We split the plane in rectangles (and semi-infinite rectangles). So that's our algorithm:

* Split the points into two halfs \[sic\] using the median value.
	* Alternate recursively between $x$ and $y$.
	* Stop splitting when there's only one point left.

If we imagine having a bounding box, we have as many rectangles as we have points.

![[Pasted image 20261110120544.png]]

We obtained this by splitting the rectangle in two recursively. That should remind us of a binary tree. How do we position the keys in the tree? We first split through $H$, so that's the root: $(H,x)$. We don't write the coordinate, we just write down that we used its $x$ coordinate. Then, $(C,y)$ and $(E,y)$. Then $(C,x), (D,x), (E,x), (F,x)$ in the level below, and at the leaves, $C,B,D,H,E,A,F,G$, with no split. It's a normal tree, there's no novelty in the type of tree (there can be no novelty there), the novelty is in the building algorithms. In algorithm theory, you define a lot of different kinds of trees; take Summet's book *Data Structures Something*, there are lots of different types of trees, they're all trees, the difference is in the algorithms.

A BST is like a 1D KDET.

The memory footprint of this data structure is $O(n)$, same as a BST. The information is only in the leaves, and the internal nodes are for guidance, it's useful that we used the same strategy for BSTs.

Now we've solved the problem of how to build the tree. Now we need to think of why it can be useful. Secondo me, find bottom left e top right vertex.

Rectangle intersection, interesting, because the intersection between two rectangles is very simple. When are two rectangles intersecting? When are they not intersecting? When the intervals in $x$ and $y$ defining the rectangles are disjoint at least in one dimension. They intersect on the plane if they intersect in both dimensions, $O(1)$.

We have a tree of rectangles. And we have a rectangle as the input for the search. Wait wait wait wait wait. We have a tree of rectangles. Are we sure we can only associate rectangles to the leaves? No, we can associate them to the internal nodes as well. We start with the bounding box, which is the bounding box, we split it in two, and then in two, and then in two. The root is the bounding box, the left child has the left half, the right child has the right half. The union of the children is the rectangle of the father. The union of all the leaves is the rectangle of the root.

> For each node $\nu$ of the tree, it exists $region(\nu)$, the rectangle associated to the node.

* Read the root
* If there's no intersection at the root, return an empty set
* The line of the root can be to the left, right, or through the query interval
	* Left: discard left subtree, recurse in the right subtree
	* Right: discard right subtree, recurse in the left subtree
	* Through: it's a bit like splitting the query rectangle in a left half and the right half, recurse with both

It can happen that a whole node/leaf rectangle is inside the query rectangle. In that case, you can report the whole subtree rooted at this node.
