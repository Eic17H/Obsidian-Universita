Recap. Polygon triangulation, a function, $PT:Dcel\to Dcel$, $PT(Dcel\ polygon) = Dcel\ triangulation_{polygon}$. The input is a polygon, the output is the same polygon plus some diagonals. What are the geometric entities in the input? Edges and vertices. In the output we have a set of triangles added to the polygon, basically a set of polygons: each of these can be called a face. Think of a graph: a graph is formed by nodes and edges, and can contain cycles. Vertices, edges and faces. It's just another way to think about relations between entities.

We have some important relations in graphs. Two of them are ==incidence== and ==adiacency== \[sic\].

* ==Incidence== is a relation between entities of different types
* ==Adjacency== is a relation between entities of the same type

So we can have two adjacent vertices, two adjacent edges, two adjacent faces. Or a face incident on an edge, an edge incident on a face, and so on.

Why are these relations important? Because we can call our output a triangle mesh, which is very important for computer graphics, because triangles are always convex, That's important, because you can get a property of a point inside the triangle using linear interpolation of its vertices, useful for example for textures.

## Storage

### Naïve method

> ==**Goal**==
> Find a "good" way to store a collection of vertices, edges and faces to efficiently ==navigate== them.

> **Definition**
> ==Mesh==: A collection of vertices, edges and faces.

A vertex is a $0\ \text D$ object, an edge is a $1\ \text D$ object, a face is a $2\ \text D$ object. We're working on a plane. We *could* work in a space, but then we'd have to deal with volumes, let's just stay on a plane.

How do we store our entities?

Let's start from the simplest one, a vertex. What is the information we need to store a vertex? For a vertex $V$, we only need a very simple data structure (call it a structure, call it a record, whatever) where you have two fields: $x$ and $y$, its coordinates. It's an ordered pair, and to store multiple vertices you can just use an array of pairs, and then you'd have $v_0$, $v_1$, $v_2$, $\ldots$.

$V$

|   $x$   |   $y$   |
| :-----: | :-----: |
| $float$ | $float$ |

|          | $x$ | $y$ |       |
| :------: | :-: | :-: | :---: |
|   $0$    |     |     | $v_0$ |
|   $1$    |     |     | $v_1$ |
| $\cdots$ |  <  |  <  |   <   |


We now have a collection of vertices. Can we describe a polygon with just a collection of vertices? No, but we can describe a cloud of points, which was the input for the convex hull algorithm.

An edge, $E$. Simple, a pair of vertices. **But**, there's already an immediate smarter solution: because we're using ==🟠open== edges and ==🟠open== faces, I'm obliged to use vertices as endpoints of edges, meaning we don't have to store all our vertices again. But let's ignore that for now.

A face, $F$. You could list all edges and vertices of the face. Could we store less? Could we just store the vertices and deduce the edges from those? It's easier to store the edges and deduce the vertices. So a face can just be a list of edges.

And each element is a list with its own length. But whatever, a list of list of pairs of floats.

What am I actually doing? I want to query incidences and adjacencies.

My queries:

> ==**Q1**==
> Given a vertex $v_i$ which are the vertices adjacent to it?

Given our list of lists of pairs of floats, how do I answer that? Check every edge, and if one of the end points is $v_i$, add the other end point to the output list of the query. Great, so I can do it! How much does it cost. With $O(n)$ vertices, we have $O(n)$ edges and $O(n)$ faces, it's a search in an unsorted set, giving us $O(n)$ time.

We can do something to improve it.

One way is to modify our data structure to add a list of adjacent vertices, so that we can answer the query in $O(1)$.

> **==Q2==**
> Given a vertex $v_i$, find all the edges incident on it.

Is our list of adjacent vertices useful for this query? No.

Solution, add an incidence table. As in, when you save a vertex, save a list of adjacent vertices, incident edges and incident faces. And so on. But that's complex and redundant, I have the same information repeated several times, so if you want to, say, remove a vertex, it's a mess. And it also wastes memory. Same logic as avoiding magic numbers in code.

### Wisdom

So, instead of encoding it explicitly, we can do it implicitly, so that we can efficiently find the answer to queries like this using the relation of incidence and adjacency implicitly encoded in our data structure. But... we should add something.

This remark should be trivial, but... the edges are ordered. If I describe my face with an ordered list of edges counterclockwise, I can say that "after this edge I can find that edge", and repeat until I'm back where I started. So for each edge I have a next edge and a previous edge.

Let's thus use a linked list of edges. Each edge stores its normal data, plus the next edge. But that means that to store a face, I can just store a single edge, because the whole face is stored implicitly in the list of edges, by paying just a little fee.

### The DCEL

To describe a face, in a DCEL, we don't use edges, but what DCELs call half-edges. Some call it a "face edge", but "half edge" is really nice, because it's like you're cutting it in two:

![[Pasted image 20261103121239.png]]

And they always go in different directions. So a DCEL doesn't store edges, but always stores half-edges.

For each vertex, we store its coordinates and just one incident edge, $V=((float,float)\ position,E\ inc)$. For each half-edge, we store the origin vertex, the next edge, and the previous edge, but also its *twin* half-edge, and the one face it's incident on, $hE = (V\ origin,\ hE\ next,\ hE\ prev,\ hE\ twin,\ F\ inc)$. A face is easy, a single half-edge since it defines a linked boundary (though the complete definition of a DCEL includes the possibility of holes, which we'll ignore), $F = (hE\ inc)$.

If $v_i.inc = e_i$, then $e_i.origin=v_i$.

(We could get rid of $prev$ but it's useful if faces are really large. It's a small redundancy, but it's worth wasting some memory to save time).

We only store actual positions, actual geometrical information in a vertex, everything else is topological relations.

To find the faces incident on a vertex, $v_i.inc.inc$. But that's only one face, we'll find the other faces later.

Our queries!

**==Q1==**:
* $v_i.inc.twin.origin$
* Then next, twin, origin, next, twin, origin, until you loop

``` JS
function findAdjacent(vi) {
	let list = [];
	let vj = vi;
	let ei = vj.inc;
	do {
		ei = ei.twin;
		vj = ei.origin;
		ei = ei.next;
		if(vj != vi) list.push(vj);
	} while (vj != vi)
}
```
