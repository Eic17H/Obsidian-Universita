Point location => trapezoidal maps. We saw a data structure that at first seems to be a tree, but isn't.

We saw that the algorithm to build $T$ and $D$ is iterative. Iterative step:$$T(S_i) \xrightarrow{S_{i+1}} T(S_{i+1})$$
Which means that when I add the segment $S_{i+1}$, I want the trapezoidal map to change accordingly. Also,$$D_i \xrightarrow{S_{i+1}} D_{i+1}$$
The input of the algorithm is the subdivision $S$ made of the segments $\{S_1,S_2,\ldots,S_n\}$

Let's start from where we were yesterday. We can say that at the very start we have just the bounding box.

![[Pasted image 20261125091637.png]]

So, we want to transform the trapezoidal map at step $0$ into the trapezoidal map at step $1$. Let's add a segment. A segment is characterized by two end points. At the same time, I want to see how the data structures evolve. That is, the table of vertices, table of edges, and table of faces. I can always call the endpoints of an edge "left" and "right", because my points are in general position.

I'm not storing the top left vertex of ==🟠$B$==, why? Because I can get it in $O(1)$ from $p_1$ and $s_t$.

We build the search data structure always with the same template. How do we read it? If I'm to the left of $p_1$, then for sure I'm in ==🔴$A$==. If I'm to its right, then compare with $q_1$. And if I'm to its left, I need to compare my $y$ position with $s_1$.

Let's insert another segment. Where do we insert it? Two things are sure:

* The segments don't cross.
* The vertices are in general position, so either the segments share an endpoint or their endpoints have different $x$ coordinates.

![[Pasted image 20261125095204.png]]

First problem: where is $s_2$ in the current trapezoidal map? Which faces are "affected" by $s_2$? As in, are currently in the trapezoidal map but won't be in the next step. To do this:
1. Find the set of faces of $T(S_i)$ traversed by $S_{i+1}$.

How do we do that? Search for the endpoints in $D_i$. So $p_2$ and $q_2$ are our query points. It's only slightly different from range search. The core intuition of this algorithm: since at step $i$ I have a well formed data structure associated to the trapezoidal map, I can use it to find where the endpoints of the inserted segment are.

We search for $p_2$ and we land on $A$. So our set is $\{A\}$, but that's not all. This is why we care about adjacency: the next one can only be $B$ or $C$, and to know which we need to compare $p_1$ with the intersection between its vertical extension and $s_2$.

And you see that thanks to our data structure, this is all $O(1)$.

Check the $x$ of $q_2$, it's smaller than the $x$ of $C.rp$, so we're done with our traversal.

Now, $A$ and $C$ are no longer there. Thus, delete their records and make new faces. What happens in the search structure? $A$ is replaced by $E$, $F$ and a portion of $G$.

![[Pasted image 20261125095809.png]]

There is a problem though. I can't have two leaves with $G$, it has to be one leaf per face. And that's why this isn't a tree.

![[Pasted image 20261125100004.png]]

That's why it's called $D$, it's not a tree, it's a ==DAG==, *direct acyclic graph*. It's not a tree, because there's more than one route from the root to a leaf, but it's acyclic because the arcs are directed. And $G$ has two paths because it has a portion of the older face $A$ and a portion of the older face $C$.

The brilliant thing about this algorithm is that, up to some depth, I'm not changing the data structure at all, only from the leaves down, the internal nodes remain. And I'm only touching the leaves corresponding to the faces traversed by the new segment.

![[Pasted image 20261125100611.png]]

That's what lets us keep the cost down.

What's the cost of searching? It's really similar to a tree, so ==if== it's well balanced the cost is $O(\log n)$. How can I obtain a well balanced data structure? I cannot do it by making some forecasts. The way the designers of the data structure did it, is with a randomized input. So, take the input of the algorithm, the segments, compute a random permutation of them, and then start with the iterative part of the algorithm. Why can this work? We would need to explore the vast territory of randomized algorithms, so just believe it. You're not certain that your structure will be well balanced, but statistically, it's extremely probable.

That's why each step adds a random segment disconnected from the existing ones, they'll connect eventually but they're shuffled for now.

What's the cost of building? Of course, the cost of search is part of it. Then there's the cost of traversal, which is output-sensitive but negligible. Do that as many times as there are segments, so $O(n) \cdot O(\log n) = O(n \log n)$.

How many leaves do I end up with? As many as there are trapezoids, $O(n)$. How many internal leaves? $O(n)$.

While building we are searching, so we had to find the cost of searching in order to build. We can do that because we're using the fact that we have a consistent trapezoidal map at the previous step to build the trapezoidal map at the next step.

Random permutations are $O(1)$, trusting your RNG.

With every insertion, we're only operating locally on the set of adjacent faces affected by the insertion. All other faces are unchanged in both data structures.

> Important: during the iterative process, all the changes (in $T(S_i)$ and $D_i$) are **local**.

So the cost is $O(k)$, where $k$ is the number of affected faces, which is incompressible. But it's negligible. And even if it wasn't negligible, it's only a factor in the building of the data structure. It's a data structure that's built once and used many times. Google Maps is updated maybe once a week, it's used millions of times daily.

What we really care about is the cost of search then, which is, hopefully, $O(\log n)$.
